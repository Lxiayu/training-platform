## 2. 系统目标与约束

### 2.1 系统定位

面向**单一中小型编程培训机构**（单校区、单法人）的一站式内部管理系统：管理端用户为机构 staff（管理员、教务、财务、前台、教师），不直接面向学员/家长提供在线服务（家长端为远期演进）。

### 2.2 建设目标

| 阶段 | 目标 | 状态 |
| --- | --- | --- |
| 一 | 静态原型：12 页面全流程演示，验证信息架构与业务规则 | ✅ 已完成（v0.2） |
| 二 | 后端服务化：FastAPI + MySQL 落地，原型前端改为调用真实 API | 🔜 本设计的目标阶段 |
| 三 | 前端工程化：迁移至 Vue 3 + TypeScript + Element Plus | 规划中 |
| 四 | 部署上线：Docker Compose 一键部署 + 日常备份运维 | 规划中 |

### 2.3 设计约束与假设

1. **单机构单校区**：无多租户需求（SaaS 化为远期演进，见《01-数据库设计》11.9）；
2. **小数据量、轻并发**：学员/缴费记录预估在万级，管理端同时在线 ≤ 20 人，无需分库分表与复杂缓存架构；
3. **单班制**：学员同一时间归属一个班级（原型行为），多班续报通过演进方案支持；
4. **资金数据敏感**：缴费记录需可追溯，采用软删除 + 备份策略；
5. **中文环境**：全中文界面与枚举值，时区固定 `+08:00`。

## 3. 总体架构设计

### 3.1 架构风格

采用**前后端分离 + RESTful API** 架构：

```
┌─────────────────────────────────────────────────────┐
│  浏览器（管理端 SPA / 阶段二的静态页面）              │
└────────────────────┬────────────────────────────────┘
                     │ HTTPS · JSON · JWT Bearer
┌────────────────────▼────────────────────────────────┐
│  Nginx（静态资源 + 反向代理 + TLS）                  │
└────────────────────┬────────────────────────────────┘
┌────────────────────▼────────────────────────────────┐
│  FastAPI 应用（uvicorn 多进程）                      │
│  ┌─────────┬─────────┬─────────┬──────────────────┐ │
│  │ API 路由 │ 服务层   │ 数据仓储  │ 公共组件         │ │
│  │ (api)   │(services)│(models) │(core: 认证/配置/日志)│
│  └─────────┴─────────┴─────────┴──────────────────┘ │
└───────┬─────────────────────────────────┬───────────┘
        │ SQLAlchemy 2.0 (异步)           │ Redis 7
┌───────▼───────────────┐   ┌─────────────▼───────────┐
│  MySQL 8.0            │   │ 缓存：配置/会话黑名单     │
│  training_platform 库  │   │（阶段二可选，先单机运行） │
│  9 张业务表（InnoDB）  │   └─────────────────────────┘
└───────────────────────┘
```

### 3.2 逻辑分层

| 层 | 职责 | 关键约定 |
| --- | --- | --- |
| 接入层 | Nginx 托管前端静态资源、反向代理 `/api`、TLS 终止 | 前后端同域部署，避免 CORS 复杂化 |
| API 层（`app/api`） | 参数校验（Pydantic）、认证鉴权、调用服务层、组装响应 | **不写业务逻辑** |
| 服务层（`app/services`） | 业务规则：删除保护、状态流转、编号生成、统计口径 | 事务边界在服务层方法 |
| 数据层（`app/models`） | SQLAlchemy ORM 模型 + Alembic 迁移 | 软删除过滤器统一注入 |
| 存储层 | MySQL 8.0（主存储）、Redis 7（配置缓存、令牌黑名单，可选） | 表结构见《01-数据库设计》 |

### 3.3 技术选型

| 领域 | 选型 | 版本 | 说明 |
| --- | --- | --- | --- |
| 后端语言 | Python | 3.12+ | 与 `pyproject.toml` 一致 |
| Web 框架 | FastAPI | 0.11x | 自动 OpenAPI 文档、Pydantic 校验、异步支持 |
| ORM | SQLAlchemy | 2.0 | 异步引擎 + 声明式模型 |
| 迁移 | Alembic | 1.x | 版本化表结构演进 |
| 数据库 | MySQL | 8.0+ | InnoDB / utf8mb4，详见《01-数据库设计》第 2 章 |
| 缓存 | Redis | 7 | 阶段二可选（配置缓存、登出令牌黑名单） |
| 认证 | JWT（PyJWT）+ bcrypt | — | 无状态令牌，详见 5.1 |
| 包管理 | uv | — | 锁定依赖、快速安装 |
| 前端（目标态） | Vue 3 + TypeScript + Element Plus | — | 阶段三迁移；阶段二沿用原型页面改造 |
| 部署 | Docker Compose | — | nginx + api + mysql (+ redis) 一键编排 |

> 阶段二的务实策略：**保留现有静态页面**，仅将 `web/js/common.js` 中的 localStorage 数据访问替换为 fetch 调用真实 API，先跑通闭环，再启动前端工程化。

### 3.4 部署架构

单机 Docker Compose 部署（机构内网或轻量云主机）：

```
docker-compose.yml
├── nginx:80/443        # 静态资源 + 反向代理 /api → api:8000
├── api (uvicorn)       # FastAPI，挂载源码或镜像内置
├── mysql:8.0           # 数据卷持久化，每日 mysqldump 备份
└── redis:7 (可选)      # 配置缓存 / 令牌黑名单
```

环境配置（数据库连接、JWT 密钥等）通过 `.env` 注入，不进代码库。

- **登录认证**：JWT 签发与校验；禁用账号在登录时与服务层双重拦截（原型已有此规则）；

## 5. 关键业务流程设计

### 5.1 登录认证流程（JWT）

```
浏览器                    FastAPI                     MySQL
  │  POST /auth/login        │                          │
  │  {username, password}    │                          │
  │─────────────────────────▶│  查 users（含禁用过滤）    │
  │                          │─────────────────────────▶│
  │                          │  bcrypt 校验 password_hash │
  │                          │  UPDATE last_login_at     │
  │◀─────────────────────────│  签发 JWT（sub=id, role, exp=8h）
  │  {token, 用户信息}        │                          │
  │  之后每次请求 Authorization: Bearer <token>           │
```

- 令牌有效期 8 小时（对应原型 sessionStorage 会话期）；
- 禁用账号：登录时拒绝；**已登录期间被禁用**的账号在下一次请求时由认证依赖拦截（`status = '禁用'` 即 401）；
- 修改密码 / 登出：阶段二采用客户端丢弃令牌 + 短有效期；如需强制失效接入 Redis 黑名单（见 9.1）。

### 5.2 通用 CRUD 与软删除流程

所有业务实体遵循统一模式：

1. **新增**：服务层事务内生成业务编号（`code`，见 5.3）→ INSERT；
2. **编辑**：按 `id` UPDATE，乐观靠 `updated_at` 变更时间戳；
3. **删除**：`UPDATE ... SET deleted_at = NOW()`（软删除），唯一编号同时改写释放（`code + '#DEL#' + id`）；
4. **查询**：全局过滤器自动追加 `deleted_at IS NULL`（ORM Base 模型统一注入，防遗漏）。

### 5.3 业务编号生成（事务取号）

原型 `nextId()`「最大序号 + 1」在并发下会重号。服务层统一实现取号器：

```
BEGIN
  SELECT MAX(序号) FROM <表> WHERE code LIKE '<前缀>%' FOR UPDATE
  新编号 = 前缀 + LPAD(最大序号+1, 3, '0')   -- XS001、KC001 …
  INSERT ...
COMMIT
```

`uk_code` 唯一索引兜底：极端并发下插入冲突即重试一次。

### 5.4 缴费登记与状态流转

```
登记（选学员自动带出班级；选班级自动带出课程价格，可改）
   │
   ▼
[待确认] ──确认到账──▶ [已支付] ──退费──▶ [已退款]
   │                    │
   └──作废──▶ [已作废] ◀─┘
```

- 流转校验在服务层：仅「待确认」可确认到账；「已退款/已作废」为终态不可再变更；
- 统计口径：收入仅计「已支付」；待确认金额单独提示（与原型三卡片一致）。

### 5.5 删除保护与级联策略

| 操作 | 规则（原型已实现，服务层 + 外键双层落地） |
| --- | --- |
| 删教师 | 仍负责班级 → 拒绝（FK RESTRICT） |
| 删课程 | 仍有班级引用 → 拒绝（FK RESTRICT） |
| 删班级 | 仍有学员 → 拒绝（FK RESTRICT） |
| 删学员 | 二次确认后**级联删除其缴费记录**（原型行为，软删除模式下同事务软删） |
| 删用户 | 不能删当前登录账号；至少保留一个启用的超级管理员 |

完整外键矩阵见《01-数据库设计》第 6 章。

## 6. 接口设计概要

> 本章只约定**资源清单与通用契约**，请求/响应字段的详细 Schema 由 FastAPI 自动生成的 OpenAPI 文档承载（`/docs`）。

### 6.1 通用约定

| 项 | 约定 |
| --- | --- |
| 基础路径 | `/api/v1` |
| 数据格式 | `application/json; charset=utf-8` |
| 认证 | `Authorization: Bearer <JWT>`（登录接口除外） |
| 统一响应 | `{ "code": 0, "message": "ok", "data": ... }`；业务错误 `code != 0` |
| 分页 | `?page=1&page_size=20`，响应 `data: { list, total, page, page_size }` |
| 业务错误码 | 401 未认证 / 403 无权限 / 404 资源不存在 / 409 业务冲突（如删除保护触发、编号重复）/ 422 参数校验失败 |
| 时间格式 | `YYYY-MM-DD`（日期）、`YYYY-MM-DD HH:MM:SS`（时间） |

### 6.2 资源清单

| 模块 | 端点 | 说明 |
| --- | --- | --- |
| 认证 | `POST /auth/login`、`GET /auth/me`、`PUT /auth/password` | 登录、当前用户、修改密码 |
| 工作台 | `GET /dashboard/summary`、`GET /dashboard/recent-classes`、`GET /dashboard/recent-payments` | 统计卡片、近期开班、最近缴费 |
| 用户 | `GET/POST /users`、`GET/PUT/DELETE /users/{id}`、`POST /users/{id}/reset-password`、`PUT /users/{id}/status` | 用户管理（限超管） |
| 教师 | `GET/POST /teachers`、`GET/PUT/DELETE /teachers/{id}` | 教师 CRUD |
| 课程 | `GET/POST /courses`、`GET/PUT/DELETE /courses/{id}` | 课程 CRUD |
| 班级 | `GET/POST /classes`、`GET/PUT/DELETE /classes/{id}` | 班级 CRUD（含报名进度派生字段） |
| 学员 | `GET/POST /students`、`GET/PUT/DELETE /students/{id}` | 学员 CRUD（删除级联缴费） |
| 缴费 | `GET/POST /payments`、`PUT/DELETE /payments/{id}`、`POST /payments/{id}/confirm`、`POST /payments/{id}/void`、`GET /payments/stats` | 登记与状态流转、统计 |
| 新闻 | `GET/POST /news`、`GET/PUT/DELETE /news/{id}`、`POST /news/{id}/view` | 发布管理、阅读计数 |
| 资源 | `GET/POST /resources`、`PUT/DELETE /resources/{id}`、`POST /resources/{id}/download` | 资源管理、下载计数 |
| 个人信息 | `GET/PUT /profile` | 当前用户资料 |
| 系统设置 | `GET/PUT /settings` | 键值配置读写（限超管） |

### 6.3 列表查询参数约定

各列表端点统一支持：关键词搜索（`keyword`，对应原型各页搜索框）、枚举筛选（`status` / `category` / `subject` / `class_id` / `method` 等）、排序（默认与原型一致：如新闻置顶优先、缴费按日期倒序）。具体可筛字段与原型各页面筛选器一一对应，详见《01-数据库设计》8.4 节（索引支撑表）。

## 7. 数据设计概要

数据模型完整设计见 **《01-数据库设计》**，此处仅摘要关键决策：

| 决策 | 内容 |
| --- | --- |
| 表规模 | 9 张核心表：users / teachers / courses / classes / students / payments / news / resources / sys_configs |
| 主键策略 | `id` 自增主键（外键关联）+ `code` 业务编号（UNIQUE，保留原型 XS001 等展示习惯） |
| 软删除 | 全表 `deleted_at`，替代原型的物理删除 |
| 密码 | bcrypt 哈希（`password_hash`），绝不存明文 |
| 枚举 | VARCHAR + CHECK 约束（20+ 组，全中文取值与界面一致），不用 MySQL ENUM |
| 状态机 | 缴费四态（待确认/已支付/已退款/已作废）、班级三态、学员三态 |
| 完整性 | 8 个外键：删除保护用 RESTRICT，删学员级联缴费用 CASCADE，删账号解绑教师用 SET NULL |
| 统计口径 | 收入仅计「已支付」；在读学员仅计「在读」；报名人数为派生值不入库 |

## 8. 非功能设计

### 8.1 安全设计

| 项 | 措施 |
| --- | --- |
| 密码 | bcrypt（cost ≥ 12）哈希存储；重置后统一 `123456` 并建议首登强制修改 |
| 认证 | JWT 8 小时有效期；服务端每请求校验账号状态（禁用即失效） |
| 授权 | 接口层角色依赖统一拦截（`require_role`）；前端入口隐藏仅是体验优化 |
| 注入防护 | SQLAlchemy 参数化查询，禁止拼接 SQL |
| XSS | 富文本（新闻正文）存储原文、输出时后端与前端双层转义（延续原型 `esc()` 策略） |
| 传输 | Nginx 统一 TLS；内网部署可选自签证书 |
| 个人信息 | 手机号/家长电话属于个人信息，列表接口可选脱敏输出（增强项） |

### 8.2 性能设计

- 数据量小（万级），**单表索引即可满足**，无需缓存热点数据；Redis 仅用于配置缓存与令牌黑名单（可选）；
- 列表接口默认分页（page_size=20），统计卡片单 SQL 聚合（见《01-数据库设计》第 8 章）；
- 连接池：SQLAlchemy `pool_size=10, max_overflow=20`。

### 8.3 可维护性

- 表结构演进一律走 Alembic 迁移，文档与迁移版本同步（双写约定见《01-数据库设计》第 12 章）；
- 服务层业务规则与《01-数据库设计》第 5/6/7 章逐条对应，测试用例按规则编号组织；
- 结构化日志（请求 ID、用户、动作），缴费与用户操作记录审计日志（演进项 11.4）。

### 8.4 可用性与备份

- 单机部署 + 每日 `mysqldump --single-transaction` 全量备份，binlog 保留 ≥ 7 天（资金数据可恢复到任意时间点）；
- 健康检查端点 `GET /api/v1/health`（Compose 探活）；
- 目标可用性：工作时间 99.5%（内部系统，允许停机窗口维护）。

## 9. 工程结构与代码规范

### 9.1 后端目录结构（阶段二骨架）

```
training-platform/
├── app/
│   ├── api/            # 路由层：auth.py, users.py, teachers.py, ...
│   ├── services/       # 服务层：业务规则、事务边界
│   ├── models/         # SQLAlchemy ORM 模型（9 张表）
│   ├── schemas/        # Pydantic 请求/响应模型
│   ├── core/           # 配置、认证（JWT/bcrypt）、依赖注入、日志
│   └── main.py         # 应用入口
├── alembic/            # 数据库迁移
├── scripts/            # seed_demo.py（演示数据导入）等
├── tests/              # pytest 单元/接口测试
├── web/                # 前端（阶段二沿用原型，阶段三迁出）
├── docs/               # 01-数据库设计.md、02-总体设计.md
├── docker-compose.yml
├── pyproject.toml      # uv 管理依赖
└── README.md
```

### 9.2 前端结构

- **阶段二**：保持 `web/` 原型结构不动，仅重写 `web/js/common.js` 中的数据访问层（localStorage → fetch API），页面与业务脚本零改动或小改动；
- **阶段三**：迁移至 Vue 3 + TypeScript + Element Plus 标准工程（`src/api`、`src/views`、`src/stores`），按 12 模块划分视图。

### 9.3 协作规范

- 依赖用 **uv** 锁定（`uv.lock` 入库）；Python ≥ 3.12；
- 代码风格 ruff + 类型检查 mypy；提交信息遵循 Conventional Commits（`feat:` / `fix:` / `docs:` …）；
- 文档即代码：设计文档与实现不同步时，以「先改文档 → 再改代码」为原则。
